Ce que vous allez tester, et pourquoi c'est construit ainsi

La plateforme réunit l'étendue d'exploitation de la version Hercules (trésorerie journalière, commandes, audit, contrôle d'accès fin, API d'export) et la profondeur d'automatisation de la paie de la version Lovable. Chaque scénario ci-dessous dit comment vérifier une fonctionnalité et pourquoi elle est conçue de cette façon.

Phase 1
Paie automatisée
Employés, barème daté, planning, saisie, primes, bulletins, courrier + PDF, archives. Détail dans le cahier n°1.
Phase 2

01

Comment procéder

  1. Environnement : deux terminaux dans app/ — npx convex dev et npm run dev (http://localhost:5173). Vous êtes Directeur (dev) · niveau 7 grâce à AUTH_DEV_BYPASS=true.
  2. Données de démo : sur le tableau de bord, cliquez dans l'ordre « Initialiser les données de démo » (Phase 1), puis « Initialiser la démo Phase 2 », « … Phase 3 », « … Phase 4 ». Tous les seeds sont idempotents (relançables sans doublon). Si les boutons n'apparaissent pas, c'est que la démo est déjà chargée.
  3. Ordre conseillé : filtrez par phase (boutons ci-dessous) et suivez les scénarios dans l'ordre — ils s'enchaînent (les données d'un scénario servent au suivant). La paie est déjà couverte par le cahier n°1 ; ici elle est résumée en un parcours express.
  4. Pour chaque scénario : dépliez, lisez le pourquoi, exécutez les étapes, comparez au résultat attendu (les chiffres sont calculés à partir des données de démo : ils doivent correspondre, sauf si vous avez déjà modifié ces données — les scénarios le précisent), puis cochez Validé.
  5. Les scénarios CLI se jouent dans Git Bash (PowerShell abîme les guillemets JSON) ; ceux marqués attention changent durablement l'état (clôture, rôles) ; ceux marqués audit exigent le rôle auditeur ou DG.
  6. Terminez par les tests automatisés (8 suites, 93 contrôles) : ils garantissent les invariants quoi que vous ayez saisi.

04

Invariants garantis (vérifiés par les tests)

Huit suites, 93 contrôles : npm run test:paie (12), test:tresorerie (13), test:fenetre (15), test:commandes (13), test:stats (8), test:audit (12), test:api (13), test:proxy (7). La logique métier est isolée dans des modules purs (convex/lib/*) : testable sans base ni serveur.

Paie : net = brut − retenues listées

Barème daté par période, CNPS plafonnée, salaire proratisé par les jours travaillés, primes/charges du registre en lignes nommées.

Trésorerie : report J-1 et chaîne

solde = J-1 + entrées − retraits par canal ; le J-1 est la dernière journée saisie ; modifier une journée recalcule les suivantes ; recette = entrées seulement.

Fenêtre de soumission

Lundi–vendredi 16h–20h heure de Douala (UTC+1). Dans la fenêtre = 1 point, hors fenêtre = accepté, marqué, 0 point.

Workflows contrôlés

Commandes en_attente → validée | rejetée → livrée, interventions ouverte → en cours → clôturée | rejetée ; transitions invalides refusées ; rejet = motif obligatoire.

Sécurité API

Clé comparée en temps constant, deux couches (proxy + backend), rate-limit et liste blanche IP, journalisation de chaque appel, jamais d'exposition directe de la base.

Gel et cloisonnement

Mois de paie ou de trésorerie clôturé = immuable ; audit réservé auditeur + DG ; jamais de plateforme sans DG actif.
